01 OMS API + Webhooks ↔ Cardio - Cardio forwards the auth request via webhook to the OMS API; OMS returns approve / decline / partial-auth. Sub-second round trip within card-network auth windows.

02 Balance & Settlement Engine ↔ Internal Ledger - Per-transaction reconciliation payloads (transaction ID, asset, amount, FX rate, fees, on-chain hash, timestamps) pushed to Block's Internal Ledger in real time, plus daily batch reconciliation files (JSON/CSV).

03 Wallet / Custody Layer ↔ IDS - Default path: Block's current wallet infrastructure serves as the funding-instrument custody layer; IDS maps cardholder identity to that wallet. Optional path: Polygon WaaS can provision and manage the wallet instead, with the same identity-to-wallet mapping synced to IDS. No dual-wallet setup - one path is active per program.

04 Settlement, Compliance & Reporting ↔ CIS / CFS - Settlement confirmations, clearing/reporting datasets, and compliance/audit records delivered to Block's CIS/CFS on the agreed batch and real-time cadence.

05 Issuing Token Service - No direct Polygon integration; token-level context flows through Cardio into the standard OMS auth payload (see note below).
Note - Issuing Token Service (network tokenization for Apple Pay / Google Pay, card-present token lifecycle) is fully Block-owned and requires no direct Polygon integration. Token-level context (token requestor ID, token state) travels with the auth request through Cardio and is passed to the OMS API as part of the standard auth payload - no separate API surface needed.
